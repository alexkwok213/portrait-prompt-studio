# Portrait Prompt Studio

## Scope

Everything is generated by **text prompt only**. The image tool never receives a
reference photograph as an input file — no attachment, no `image1`, no
image-to-image. Photographs enter this workflow in one way only: the agent looks
at them with a vision tool, reverse-engineers them into written prompts, and
stores those prompts as templates. That is the whole of the "photo" path.

Support fictional people of all ages. Under-18 portraits use age-appropriate
clothing, ordinary expressions and settings. Do not carry adult seductive
styling into child portraits. A study photograph supplies photography reference,
not permission to reuse its original person's identity or commercial likeness.

## The single route, and its two starting points

Generation is always text-to-image. What differs is where the prompt comes from.

| The user provides | Starting point | Spec |
|---|---|---|
| A description, no photo | Build the prompt directly | `references/text-to-image.md` |
| A photo to learn from | Reverse-engineer into a template, then edit it | `references/template-workflow.md` |
| A saved template + a change request | Edit the template's elements | `references/template-workflow.md` |

There is no fallback between these. A photo is never uploaded to the image tool;
if a user asks for a face that text cannot produce, the answer is a better
description or a different template — not a different generation mode.

## Scope of what may be reused from a source photograph

When reverse-engineering, separate three things and keep them separate in the
template:

- **Reusable photography**: composition, camera height and distance, light
  direction and hardness, depth-of-field behaviour, colour and grain, posture
  and hand placement, the moment the expression belongs to.
- **New identity**: age, ethnicity, facial structure, hair, clothing. Always
  assigned fresh. Never a copy of the source person's identifiable features.
- **Design decisions**: distances, object placement and anything the photograph
  cannot prove. These are marked as design, not reported as observations.

## Route 1 — build from a description

1. **Resolve the brief.** Record age, setting, crop, aspect ratio, style and
   length. Ask only for what is genuinely blocking.
2. **Write a full sentence-level prompt.** Follow `references/text-to-image.md`:
   every dimension is a complete sentence with subject, feature and state —
   never a comma-separated label stream. Cover the dimension skeleton, give the
   gaze a state word, write the light source with all four factors, write the
   background by exclusion, and keep the expression as one moment in progress
   where eyes, cheeks, nose and lips agree.
3. **Stay physical.** `references/realism.md` applies. Do not append film grain,
   rim light, shallow depth of field or creamy skin just to sound polished; let
   the scene decide. A phone snapshot is written as a phone snapshot.
4. **Watch for the templated face.** If output repeats round faces, bright eyes,
   even skin and a fixed smile, reduce the idealizing words and pick a couple of
   ordinary distinguishing features. Changing one relevant constraint beats
   adding more realism keywords.

## Route 2 — reverse-engineer a photo into a template

1. **Look at the photograph.** Use a vision tool on the local original. Do not
   work from a filename, a caption or a remembered description — reading text
   about a photograph is not reverse-engineering the photograph.
2. **Run all seven steps in `references/photo-reverse-engineering.md`.** Read
   the whole frame before writing anything; locate the light source; write the
   person and the expression as a moment in progress; write the pose and hands
   joint by joint; describe clothing by material; describe the background with
   distances; describe the imaging. The lighting step carries the most weight —
   do not skim it.
3. **Make every claim traceable.** Each answer needs to record how it was
   determined, not just the conclusion, and each sentence must point at a
   specific place in the frame. "Soft light" is not a description; "her left
   cheek is brighter, with a faint shadow beside her right nostril" is.
4. **Sort into three buckets** (`template-workflow.md` §三): reusable
   photography relations, freshly assigned identity, and new design decisions.
   Camera settings, lighting rigs and retouching are inference unless provable.
5. **Write the template.** Produce Chinese and English versions describing the
   same scene, split into swappable elements E1–E10, and fill the sectioned
   report format at the end of `photo-reverse-engineering.md`. E7 light, E9
   framing and E10 imaging are protected by default.
6. **Assign a new identity.** The template keeps the photography and changes the
   person. Say so in the template header. Never carry over the source person's
   identifiable features.
7. **Save it under `templates/<slug>/`** with `preview.png`. Source photographs
   live in `templates/photos/`, never inside the template directory — see
   `references/photo-reverse-engineering.md` for the layout.

## Applying a change request to a template

When the user says "换成红色连衣裙", "改成短发", "背景换成海边":

1. Locate the element in the template's element table.
2. Rewrite **only that element's** sentences in both language versions.
3. Leave the other elements byte-identical — that is what makes a template
   reusable. Changing more than asked loses the point of having a template.
4. Note in the output which elements changed and which were held.
5. If the requested change contradicts the physics the template depends on — for
   example a heavy garment replacing a light one under the same hard side light —
   say so, and either adjust the light or flag the conflict.

## Inspect the result

Apply `references/self_check.md` to the generated image, not just the wording.
Both routes end here; the visual acceptance step is identical. Report remaining
problems. If revision is needed, change the relevant face, lighting, pose or
depth relationship; do not keep adding generic realism keywords. Preserve
original and revised outputs.

## Reference files

- `references/text-to-image.md`: sentence-granularity spec, dimension skeleton,
  8 hard rules, expression-as-moment, template-face correction order, fill-in
  skeleton. **The default spec for Route 1.**
- `references/photo-reverse-engineering.md`: the seven-step reverse-engineering
  procedure — how detailed a photo analysis has to be, how to locate the light,
  what each section must answer, and the full report format. **Read this before
  Route 2.**
- `references/template-workflow.md`: three-bucket split, element table E1–E10,
  protected elements, change-request handling, physical conflict table.
- `references/realism.md`: physical scene coherence, natural light, camera
  height, facial-template correction loop. Applies to both routes.
- `references/self_check.md`: Route 1 wording checks, Route 2 template checks,
  and the shared visual acceptance table applied to the generated image.
- `references/children-photo-cases.md`: source-based child-photography learning.
- `references/deposition.md`: historical style notes, retained for inspection
  only; its ideal-face formulas are not the default workflow or acceptance
  standard.
- `assets/template_browser.html`: browse, read and edit templates, emit a prompt
  packet. It does not call any image tool. Regenerate its data with
  `python3 build_templates.py` after editing any `template.md`.
- `assets/portrait_generator-legacy.html`: old field generator, retained for
  inspection only.

## Where things live

```
templates/photos/      全部模板照片集中存放，命名 <slug>__<变体>.png
templates/<slug>/      模板本体 template.md + preview.png（验证模板是否成立）
output/                出图与替换测试的提示词归档
```

Source photographs go in `templates/photos/`, not inside each template
directory — one photo may serve several templates, and keeping them apart stops
an original from being mistaken for a generation input. `preview.png` inside a
template directory is the generated proof that the template works; it is not a
source photograph.

## Completion evidence

For an image task, save the actual prompt, the route used, the template slug if
one was used or created, the generated image path, and brief visual findings with
the output. For a template task, save the template directory. Never claim that a
source photograph has been learned by the model, never report a photograph as
attached to a generation call, and never claim references guarantee elimination
of AI artifacts.
